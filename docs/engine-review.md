## 二、引擎：慢，而且战术上看不见杀

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| E1 | 搜索很慢：约 700–900 节点/秒 | `evaluate()` 每次 1.2 ms（15×15，每个叶子都把约 76 条线 × 45 个棋型用 `str.find` 全盘重扫一遍）；`candidate_moves()` 每个内部节点 0.9 ms | 2 秒内只能完成 4–5 层 |
| E2 | 找不到连续冲四（VCF）必胜 | 从它自己的对局中截取 10 个 7–17 层的 VCF 局面，在网页默认的 2 秒预算下只找到 **1/10** | 演示时会出现"明明能赢却不杀" |
| E3 | 防守端看不见对方的 VCF | 只给它加上 VCF 进攻，对原版仍是 **8:8**（16 局，交换先后手），没有变强。说明输棋主要发生在"走进对方的杀"上。加了 VCF 防守的对照实验见下方"补充结果" | 同学稍微会下就能赢它 |
| E4 | 评估函数不区分轮到谁走（没有先手价值） | 同一局面下，深度 3 / 4 / 5 给出的最佳着法来回跳：[8,4] → [9,6] → [8,4]，奇偶层震荡 | 着法不稳定，棋力偏弱 |
| E5 | 棋盘边缘不算阻挡 | 贴边的冲四估值为 **0**；被对方棋子挡住的同样冲四估值为 10000。贴边的眠三也是 0 | 边路攻防判断错误 |
| E6 | 迭代加深是纯开销 | 下一轮不复用上一轮的主变例排序；没有置换表、杀手着法、历史启发 | 浪费约 30% 的时间，也拿不到迭代加深应有的剪枝收益 |
| E7 | 服务端在课堂互评时会顶不住 | 搜索跑在线程里，受 GIL 限制；只有 `SEARCH_SLOTS=2`，第三个请求直接返回 429"AI 忙" | 互评时二十几个人同时玩，会大量报"AI 忙" |

## 三、实验与报告

| # | 问题 | 改法 |
|---|---|---|
| R1 | 只测了深度 1–3，Minimax 与 Alpha-Beta 的节点差距只有 70% | Minimax 测到深度 4，Alpha-Beta 测到 5–6。指数级的差距要到这个深度才看得出来 |
| R2 | **棋盘大小的影响几乎看不出来**：深度 3 时 9 / 13 / 15 三种棋盘的节点数都是 643.7，图中三条曲线重合。原因是候选上限 cap=8 把分支因子固定住了，而且三种棋盘用的是同一组居中开局，最终只有评估耗时随棋盘变大 | 增加两组对照：一是不设上限、以半径或全盘空点作为候选，此时分支因子会随棋盘变大；二是小棋盘全宽 Minimax，展示 b^d 爆炸 |
| R3 | 每种棋盘只用 3 个开局局面，棋子很少 | 改用至少 20 个来自真实对局的中局局面 |
| R4 | 只测了时间和节点，没有测棋力 | 增加"深度 d 对深度 d+1"的对弈胜率，以及候选上限对棋力的影响 |
| R5 | **创新章节只有规划**，原文写的是"尚无训练结果" | 这是创新分最大的缺口，见第四节 |
| R6 | 只有 PDF 和 HTML，没有 Word | 需要和用户确认老师要什么格式 |
| R7 | 版面较素，第 1 页下半页是空白 | 等内容定稿后统一排版 |

## 补充结果：VCF 攻守对照（16 局，每步 1 秒，交换先后手，`experiments/probe/probe_match2.py`）

- 原版的走法中，有 **53/361（15%）** 走完之后对方立刻拥有 VCF 必胜。原版输掉的 8 局里，**8 局都出现过这种失误**。
- 在根节点加一层"VCF 防守过滤"（候选走完后对方若有 VCF 就不走）：总比分 8:7:1（胜:负:和），提升不明显。
- 先手优势压倒一切：两边执黑时大多获胜。执白时，加了防守的版本赢 2/8，原版赢 1/8。
- 结论：只在根节点做 VCF 过滤远远不够。需要的是这几样一起上：更快的搜索（更深）、修好评估函数（E4、E5），以及把 VCF/VCT 放进搜索内部（威胁延伸），而不是只放在根节点外挂。报告中所有对弈实验都必须交换先后手。
